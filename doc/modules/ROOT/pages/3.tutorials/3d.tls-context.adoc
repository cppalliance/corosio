= TLS Context Configuration
:page-mode: tutorial

This tutorial covers how to configure TLS contexts for secure connections.
A cpp:tls_context[] stores certificates, keys, and settings that define how
TLS connections are established and verified.

[NOTE]
====
Code snippets assume:
[source,cpp]
----
include::example$snippets/3d_tls_context.cpp[tag=assume]
----
====

== Introduction

The cpp:tls_context[] class is a portable abstraction for TLS configuration that
works across the TLS backends (OpenSSL and WolfSSL). It
handles:

* Loading certificates and private keys
* Configuring trust anchors for peer verification
* Setting protocol versions and cipher suites
* Configuring certificate verification behavior
* Managing revocation checking (CRLs)

Use cpp:tls_context[] to configure TLS settings once, then pass it to TLS streams
for establishing secure connections.

[NOTE]
====
On WolfSSL, some features depend on how the library was built:

* `set_default_verify_paths()` needs `WOLFSSL_SYS_CA_CERTS`
  (`--enable-sys-ca-certs`, on by default) to load the system store.
* `set_verify_callback()` needs `WOLFSSL_ALWAYS_VERIFY_CB`, which
  `--enable-opensslextra` defines.
* `set_alpn()` needs `HAVE_ALPN` (`--enable-alpn`).
* CRL checking needs `HAVE_CRL` (`--enable-crl`).
* Verifying an IP literal passed to `tls_stream::set_hostname()` needs
  both `OPENSSL_EXTRA` and `WOLFSSL_IP_ALT_NAME`
  (`--enable-opensslextra --enable-ip-alt-name`).

Except for the system store, a missing feature fails the handshake with
`std::errc::function_not_supported` rather than failing open.
====

== Construction

A cpp:tls_context[] is a shared handle to an opaque implementation. Copies share
the same underlying state, making it easy to pass contexts by value and share
them across multiple TLS streams.

IMPORTANT: Don't modify a context after creating a stream from it. Most
settings are captured at the first handshake of any stream using it;
others, such as callbacks, are read later. A change may therefore apply
partly or not at all. If you need a different configuration, create a
separate context.

== Trust Anchors

Trust anchors are root CA certificates used to verify peer certificates.
Without trust anchors, certificate verification fails.

=== Using System Trust Store

For HTTPS clients connecting to public servers, use the system's CA store:

[source,cpp]
----
include::example$snippets/3d_tls_context.cpp[tag=system_trust,indent=0]
----

What "system store" means depends on the backend:

* OpenSSL: the CA file and directory OpenSSL was built with, under its
  `OPENSSLDIR` (typically `/etc/ssl` on Linux). The `SSL_CERT_FILE` and
  `SSL_CERT_DIR` environment variables override them. OpenSSL does not
  read the macOS Keychain or the Windows Certificate Store. On those
  platforms, supply trust anchors with `load_verify_file()` unless that
  OpenSSL installation ships its own CA bundle.
* WolfSSL: on Linux it reads the first readable CA directory among
  `/etc/ssl/certs` and the `/etc/pki` locations. On macOS it reads the
  user, admin, and system trust settings. On Windows it reads the Root and
  CA stores. This requires a build with `WOLFSSL_SYS_CA_CERTS`. Without it, supply
  trust anchors explicitly with `load_verify_file()` or
  `add_certificate_authority()` (below).

=== Custom Verification

For advanced use cases, install a custom verification callback. It runs
during the handshake; return `true` to accept the certificate or `false`
to reject it. Inspect the certificate portably with
`verify_ctx.certificate()` (its DER bytes); `native_handle()` also exposes
the backend's `X509_STORE_CTX*`.

[source,cpp]
----
include::example$snippets/3d_tls_context.cpp[tag=verify_callback,indent=0]
----

[NOTE]
====
Which certificates the callback sees depends on the backend:

* OpenSSL — invoked for every certificate, including ones that passed. It
  can therefore both relax verification (accept a rejected cert) and
  tighten it (reject an otherwise-valid cert, as pinning does).
* WolfSSL with `WOLFSSL_ALWAYS_VERIFY_CB` (via `--enable-opensslextra`) —
  same as OpenSSL.
* WolfSSL without it — the library invokes the callback only on failure,
  so it cannot be honored on success. To avoid silently ignoring a
  tightening callback (which would fail open), a context carrying a
  callback instead fails the handshake with
  `std::errc::function_not_supported`. Rebuild WolfSSL with
  `WOLFSSL_ALWAYS_VERIFY_CB`, or omit the callback.
====

== Error Handling

All fallible operations return `std::error_code`. Check the return value
to detect errors:

[source,cpp]
----
include::example$snippets/3d_tls_context.cpp[tag=error_handling,indent=0]
----

The setters only record configuration, so few of them can fail. Those
that read a file report one that cannot be opened, and `set_alpn()`
rejects a malformed protocol name. Content is decoded when the native
context is first built. An invalid certificate or key format, a key that
doesn't match its certificate, or a wrong passphrase therefore surfaces
as a handshake failure.
