= Reference
:page-mode: reference

This page groups the public Corosio API by purpose.
Each name links to its generated reference page.
The xref:reference:boost/corosio.adoc[index by kind] lists these names, plus namespaces and operators, by entity kind.

All names are in namespace `boost::corosio`.
The socket options are in cpp:socket_option[].
The page of each type lists its operators.

Corosio builds on Boost.Capy, which provides tasks, executors, buffer sequences, the stream concepts, and `capy::results`.
See xref:4.guide/4b.concurrent-programming.adoc[Concurrent Programming], xref:4.guide/4n.buffers.adoc[Buffer Sequences], xref:4.guide/4g.composed-operations.adoc[Composed Operations], and xref:4.guide/4m.error-handling.adoc[Error Handling].

Two public Corosio namespaces are not in the generated reference.
`boost::corosio::test` holds the test tools that xref:5.testing/5.intro.adoc[Testing] describes.
<<socket-options>> describes `boost::corosio::native_socket_option`.

[#io-context-and-io-backends]
== I/O Context and I/O Backends

An cpp:io_context[] runs the event loop that completes I/O operations.
A completed operation resumes the awaiting coroutine through that coroutine's executor.
Each I/O object belongs to one cpp:io_context[].
By default, an cpp:io_context[] uses IOCP on Windows, epoll on Linux, kqueue on BSD and macOS, and select on other POSIX systems.
Each I/O backend has a tag type, such as cpp:epoll_t[], and a tag value, such as cpp:epoll[].
Each tag type and tag value exists only on platforms where its I/O backend is available.
The io_uring I/O backend, cpp:uring_t[], needs Linux and liburing, and an cpp:io_context[] never uses it by default.
Pass a tag value to the cpp:io_context[] constructor to choose the I/O backend at compile time.
cpp:io_context_options[] holds the runtime tuning settings, including the cpp:locking_mode[].
See xref:4.guide/4c.io-context.adoc[I/O Context] and xref:4.guide/4c2.configuration.adoc[Configuration].

[#io-objects-and-streams]
== I/O Objects and Streams

Sockets, acceptors, files, resolvers, signal sets, and the descriptor and handle types derive from cpp:io_object[].
cpp:io_stream[] combines cpp:io_read_stream[] and cpp:io_write_stream[].
A function that takes an cpp:io_stream[] reference accepts a TCP socket, a Unix domain stream socket, a stream file, or a stream descriptor or handle.
cpp:shutdown_type[] selects which directions a socket's `shutdown` closes.
cpp:wait_type[] selects the readiness condition that completes the `wait` operation of a socket, an acceptor, or a cpp:posix_stream_descriptor[].
cpp:native_handle_type[] is the type of a platform descriptor or handle.
See xref:4.guide/4d.sockets.adoc[Sockets] and xref:4.guide/4r.wait.adoc[Readiness Wait].

[#addresses-and-endpoints]
== Addresses and Endpoints

An cpp:endpoint[] pairs an IP address with a port.
An cpp:ip_address[] holds either an cpp:ipv4_address[] or an cpp:ipv6_address[].
cpp:family[] names the address family of a socket or an address.
The `make_` functions in this section parse a string into an address or an endpoint.
cpp:detect_endpoint_format[] reports which cpp:endpoint_format[] a string uses.
See xref:4.guide/4f.endpoints.adoc[Endpoints].

[#name-resolution]
== Name Resolution

A cpp:resolver[] resolves a host name and a service to a list of endpoints.
It also resolves an endpoint back to an cpp:endpoint_name[], which holds a host name and a service name.
cpp:resolve_flags[] and cpp:reverse_flags[] change how each kind of query works.
cpp:host_name[] returns the name of the local machine.
See xref:4.guide/4j.resolver.adoc[Name Resolution] and xref:3.tutorials/3c.dns-lookup.adoc[DNS Lookup Tutorial].

[#tcp]
== TCP

A cpp:tcp_socket[] connects to a peer, then reads and writes a byte stream.
A cpp:tcp_acceptor[] listens on an endpoint and accepts inbound connections.
cpp:connect[] tries each endpoint in a range, in order, until one connects.
The range is often the list of endpoints that a cpp:resolver[] returns.
cpp:tcp_server[] manages a pool of reusable workers that handle accepted connections.
See xref:4.guide/4d.sockets.adoc[Sockets], xref:4.guide/4e.tcp-acceptor.adoc[Acceptors], and xref:4.guide/4k.tcp-server.adoc[TCP Server].

[#udp]
== UDP

A cpp:udp_socket[] sends and receives datagrams.
In connectionless mode, each send names its destination, and each receive reports its sender.
In connected mode, `connect` sets a default peer that send and receive use.
cpp:message_flags[] modifies a single send or receive on a UDP socket or a Unix domain datagram socket.
See xref:4.guide/4q.udp.adoc[UDP Sockets].

[#unix-domain-sockets]
== Unix Domain Sockets

A Unix domain socket connects processes on the same machine through a filesystem path, which a cpp:local_endpoint[] holds.
cpp:local_stream_socket[] and cpp:local_stream_acceptor[] work like their TCP counterparts.
cpp:local_datagram_socket[] sends and receives datagrams, on POSIX systems only.
cpp:connect_pair[] connects two sockets to each other, so the caller needs no path.
cpp:bind_option[] controls whether an acceptor's `bind` first removes an existing socket file at the path.
See xref:4.guide/4p.unix-sockets.adoc[Unix Domain Sockets].

[#socket-options]
== Socket Options

A socket option changes how the operating system handles a socket.
Pass one to `set_option` or `get_option` on a socket or an acceptor.
Each concrete option in cpp:socket_option[] supplies the platform's protocol level and option name, so the calling code needs no platform headers.
Most on-off options derive from cpp:socket_option::boolean_option[], and the buffer-size options derive from cpp:socket_option::integer_option[].
The header `<boost/corosio/native/native_socket_option.hpp>` defines the same options inline, in namespace `boost::corosio::native_socket_option`, except any that the platform lacks, such as `reuse_port` without `SO_REUSEPORT`.
That header includes the platform's socket headers.
See xref:4.guide/4a.tcp-networking.adoc#_tcp_nodelay[TCP_NODELAY] and xref:4.guide/4a.tcp-networking.adoc#_so_reuseaddr[SO_REUSEADDR] in the TCP/IP guide.
See also the xref:4.guide/4q.udp.adoc#_socket_options[Socket Options] and xref:4.guide/4q.udp.adoc#_multicast[Multicast] sections of the UDP guide.

[#delays-and-timeouts]
== Delays and Timeouts

`co_await` cpp:delay[] to suspend a coroutine for a duration or until a time point.
A stop request on the coroutine's stop token ends the delay early.
cpp:timeout[] races an operation whose result is a `capy::results` against a deadline.
A delay for a duration, or until a steady-clock time point, is a cpp:delay_awaitable[].
A delay until a time point on any other clock is a cpp:clock_delay_awaitable[].
On another clock, a wait-traits policy sets how long each underlying wait lasts before the delay reads the clock again.
The default policy, cpp:wait_traits[], waits for the full remaining time.
A custom policy satisfies cpp:WaitTraits[].
See xref:4.guide/4h.timers.adoc[Delays and Timeouts] and xref:3.tutorials/3f.reconnect.adoc[Reconnect with Backoff].

[#native-descriptors-and-handles]
== Native Descriptors and Handles

These types adopt a descriptor or handle that other code opened, and run its I/O on an cpp:io_context[].
On POSIX systems, a cpp:posix_stream_descriptor[] drives a descriptor such as a pipe, a FIFO, or a terminal.
On Windows, cpp:win_stream_handle[] and cpp:win_random_access_handle[] drive overlapped handles.
A cpp:win_object_handle[] waits on a Windows kernel object.
See xref:4.guide/4s.native-descriptors.adoc[Native Descriptors and Handles].

[#tls]
== TLS

A cpp:tls_context[] holds the certificates, keys, and protocol settings that a TLS stream uses.
A cpp:tls_stream[] runs a TLS session over another stream.
It encrypts the data it writes and decrypts the data it reads.
cpp:openssl_stream[] and cpp:wolfssl_stream[] implement it with OpenSSL and with WolfSSL.
A custom verification callback receives a cpp:verify_context[].
The `wolfssl_supports_` functions report whether the WolfSSL build supports a feature.
See xref:4.guide/4l.tls.adoc[TLS Encryption] and xref:3.tutorials/3d.tls-context.adoc[TLS Context Configuration].

[#errors]
== Errors

Operations report runtime failures as a `std::error_code`, alone or in a `capy::results`.
cpp:error[] holds Corosio's own error code, `already_open`, its one value.
Most failures that Corosio detects itself use `std::errc` codes instead.
cpp:make_error_code[] makes a `std::error_code` from an cpp:error[] value.
An error from the OpenSSL error queue uses the category that cpp:openssl_category[] returns.
OpenSSL errors from the system library, `ERR_LIB_SYS`, use `std::system_category()` instead.
An error from `wolfSSL_get_error` uses the category that cpp:wolfssl_category[] returns.
See xref:4.guide/4m.error-handling.adoc[Error Handling].

[#native-types]
== Native Types

Each type in this section derives from the type with the same name minus the `native_` prefix.
It takes a tag value from <<io-context-and-io-backends>> as a template argument, as in `native_tcp_socket<epoll>`.
The asynchronous operations of these types call that I/O backend directly, so the compiler can inline the whole call chain.
cpp:native_io_context[] does the same for its event loop functions, such as `run`.
A function that takes the base type also accepts the native object.
Calls through the base type use virtual dispatch.
xref:4.guide/4c2.configuration.adoc[Configuration] shows how to construct a cpp:native_io_context[] with options.
